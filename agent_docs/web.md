# apps/web

Next.js 15 (App Router), React 19, Tailwind CSS 4, next-intl 4, Better Auth, `motion`, `recharts`, `colyseus.js`. Alias `@/*` → `apps/web/src/*`.

## Arborescence

```
src/
  middleware.ts              next-intl : préfixe /fr ou /en (exclut /api, /_next, fichiers)
  i18n/                      routing (locales fr, en ; défaut fr), navigation, request
  app/
    [locale]/                Toutes les pages : accueil, games (/modes y redirige), solo, online, lobby/[code],
                             report/[id], learn (techniques de calcul) et learn/[technique] (entraînement), dashboard, leaderboard/[game]/[mode], player/[id], profile (onglets : profil, friends, preferences), friends (redirige), guild, login, signup, forgot/reset-password,
                             legal, privacy, terms (textes légaux), feedback (retours),
                             admin/ (panel administrateur : vue d'ensemble, games, solo, feedback, users/[id])
    api/auth/[...all]/       Handler Better Auth
    api/game-token/          Émet le JWT pour rejoindre un lobby
    api/solo-results/        Rejoue et enregistre une partie solo (connecté uniquement)
    api/avatar/              POST photo de profil (multipart `file`), DELETE la retire ; api/avatar/[id] la sert (soi-même et amis seulement)
    api/friends/             GET liste, POST demande ({ handle } ou { userId }), PATCH accepter / DELETE retirer ({ userId })
    api/invites/             GET invitations reçues (et signal de présence pour la guilde), POST inviter un ami ({ userId, code }), DELETE ignorer ({ id })
    api/guild/               GET sa guilde et invitations reçues, POST fonder ({ name }), PATCH renommer (chef), DELETE quitter ;
                             members (PATCH nommer chef, DELETE exclure : { userId }, chef), invites (POST { handle } ou { userId },
                             PATCH accepter / DELETE refuser ou annuler : { id }), crest (POST / DELETE, chef ; crest/[id] le sert), lobby (POST { code })
    api/feedback/            POST un retour ({ kind, message, contact?, page?, locale }), connecté ou invité
    api/admin/rooms/         GET parties en cours (relaie le serveur de jeu), admin seulement
    api/admin/solo/          GET parties solo en cours et récentes, admin seulement
    api/solo-activity/       POST suivi d'activité d'une partie solo (start → id, ping / end / quit), invités compris, rate limit par compte ou IP
    api/profile/title/       PATCH porte un titre possédé ({ titleId | null }), 403 `not-owned` sinon
    api/achievements/seen/   POST marque les succès du joueur comme vus
    api/daily/               POST calcul du jour ({ action: state | start | next | answer, token, value }), invités compris : le serveur pose les calculs et tient le chrono
    api/admin/feedback/      PATCH traité / rouvert ({ id, resolved }), DELETE ({ id }), admin seulement
    globals.css              Thème « cahier Seyès » (variables CSS)
  components/                Composants partagés (Keypad, OperatorPad, ExpressionBuilder / TileExpression, BombStage,
                             TimerBar, CalcLine, GameReportView…)
  lib/                       auth (serveur), auth-client, admin (serveur), colyseus, email, sound, storage, names, format,
                             answer (saisie → réponse selon le calcul, séparateur énoncé / solution)
messages/fr.json, en.json    Traductions
```

## Conventions

- **Pages** : composant serveur `page.tsx` (lit `params.locale`, appelle `setRequestLocale`, `generateMetadata` via `getTranslations`) qui rend un composant client `XxxClient.tsx` / `XxxView.tsx` marqué `"use client"`.
- **Référencement** : `@/lib/seo` donne `publicPage(locale, path, title, description?)` (canonical, Open Graph) aux pages publiques et `NO_INDEX` aux pages de compte, de partie et de joueur. Une page publique va aussi dans `app/sitemap.ts`, sa description dans `meta.*`, et son titre principal est un `<h1>`. Le `hreflang` vient de l'en-tête `Link` posé par le middleware next-intl. Ne pas bloquer une page `NO_INDEX` dans `app/robots.ts` : le robot doit la lire pour voir la consigne. `opengraph-image.tsx` dessine l'aperçu des liens partagés.
- **Navigation** : importer `Link`, `redirect`, `useRouter`, `usePathname` depuis `@/i18n/navigation`, jamais depuis `next/link` / `next/navigation`, pour garder le préfixe de langue.
- **Traductions** : aucun texte en dur dans l'UI. Toute nouvelle clé va dans **les deux** fichiers `messages/fr.json` et `messages/en.json`. Le français est la langue de référence (tutoiement, typographie française : `’`, espaces avant `: ; ! ?`, « guillemets »).
- **Auth** : `getSession()` de `@/lib/auth` côté serveur (fichier `server-only`) ; `@/lib/auth-client` côté navigateur.
  - Le pseudo est nettoyé et validé côté serveur (`databaseHooks` → `cleanName`, erreur `INVALID_NAME`) : l'API Better Auth est appelable sans passer par le formulaire.
  - Rate limit Better Auth stocké en base (`rateLimit.storage: "database"`, table `rate_limit`), actif en production seulement ; réponse 429 → `auth.tooManyRequests`. `AUTH_RATE_LIMIT_DISABLED=1` le coupe, réservé aux tests e2e.
  - `revokeSessionsOnPasswordReset` : un « mot de passe oublié » ferme toutes les sessions du compte (un vol de compte ne survit pas à la réinitialisation).
  - En production, `assertProductionSecrets` (`lib/env.ts`, appelé en tête de `lib/auth.ts`) refuse de démarrer avec un secret d'exemple ou trop court : Better Auth ne refuse que son propre secret par défaut.
  - En production : `BETTER_AUTH_URL` obligatoire (sinon erreur au démarrage), et sans `RESEND_API_KEY` le contenu des e-mails n'est jamais logué (il contient des liens de réinitialisation).
- **Routes API** : valider le corps avec Zod (`safeParse`), répondre `{ error: "code" }` avec le bon statut HTTP.
- **Accès base** : uniquement via `@calculus/db` (fonctions exportées ou `prisma`), jamais côté client.
- **Style** : réutiliser les variables CSS de `globals.css` (`--ink`, `--paper`, `--hl`, `--margin-red`, `--font-display`, `--font-hand`…) plutôt que des couleurs en dur. Polices : Bricolage Grotesque + Caveat (`next/font/google` dans `[locale]/layout.tsx` : téléchargées au build, servies par le site, jamais de requête vers Google chez le visiteur).
- **Rythme vertical (alignement sur le quadrillage)** : petite ligne `--sub` = 8 px, grand carreau `--grid` = 32 px, colonnes à partir du bord du texte (`--pad`). Ce qui est posé sur le papier a des hauteurs, marges et écarts multiples de `--sub`, **bord compris** (bord 1,5 px + rembourrage 22,5 px = 24 ; sinon trait en `box-shadow` intérieur, qui ne compte pas dans la hauteur). Texte courant : `line-height` 24 px. Le bloc « Rythme vertical » de `globals.css` arrondit la hauteur de ligne des titres, paragraphes, `li`, `.lede`, `.hint`, `.note`, `.tag`, `.calc` de `main` et pose leur ligne de base sur une petite ligne (`top` relatif < 8 px) ; réglage par élément avec `--leading` (ratio avant arrondi) ou `--lh` (valeur fixe). Les surfaces opaques (cartes, panneaux, tableaux) en sont exclues : seule leur hauteur totale compte. Pas de `gap` / `padding` en dur hors du pas dans les `style={{ }}`. Pour vérifier une page : la ligne de base d'un texte posé sur le papier doit tomber à ±0,3 px d'un multiple de 8 depuis le haut de `body`.
- **Thème clair / sombre** : les jetons sombres de `globals.css` s'appliquent selon `prefers-color-scheme`, ou via `data-theme="light|dark"` sur `<html>` quand le joueur choisit avec le bouton de `HeaderTools` (stocké dans `localStorage` `calculus:theme`, posé avant le rendu par `themeInitScript` de `@/lib/theme`). Toute nouvelle couleur doit être un jeton défini dans **les deux** blocs sombres (media query et `:root[data-theme="dark"]`), jamais une couleur en dur.
- **Techniques de calcul** : `/learn` (lien « Techniques » de `Header`) montre un niveau à la fois : onglets `.board-tabs` (liens vers `?level=1..5`, validé par Zod, niveau 1 par défaut, `aria-current`), puis une fiche bristol « À retenir » (`.technique-card`, `id` = id de la technique) par technique de `techniquesOfLevel` : kicker, nom, principe, exemple en grand (`TECHNIQUES[id].example`), étapes (`TechniqueSteps explain={false}` : sans la phrase, déjà dite par le principe), puis « S’entraîner → » (libellé accessible `learn.trainOn`). Liens niveau précédent / suivant en bas. Pas de tableau noir : le thème sombre en est déjà un. Un lien vers une technique s'écrit `/learn?level=<niveau>#<id>` (la fiche visée est encadrée par `:target`) ; un ancien `/learn#<id>` est rechargé sur le bon niveau par `LearnHashRedirect`. `TechniqueSteps` (`components/`, sans `"use client"`) affiche `techniques.<id>.how` rempli avec `hint.params` (ICU : `plural =1` pour les variantes, comme `minus` ou `below`), puis les calculs de `hint.steps`. Toute nouvelle technique demande ses trois textes dans les deux langues, avec les paramètres que son `explain` renvoie.
- **Entraînement** : `/learn/<techniqueId>` (bouton « S’entraîner » de chaque carte ; id validé par `isTechniqueId`, sinon 404). `PracticeClient` enchaîne `generateDrill(id, seed, index)` (graine `randomSeed()` tirée après le premier rendu, pour éviter un écart d'hydratation), saisie par `CalcLine`, puis le résultat et `TechniqueSteps` avec `explainTechnique(id, text)` (la technique entraînée, même si une autre passerait avant). Chrono facultatif (sans, 10 s, 20 s, `TimerBar`) ; série et réussites dans la marge. Hors classement : rien n'est envoyé au serveur ni enregistré.
- **Conseils en fin de partie** : dans `GameReportView` → `Review`, chaque manche du calcul mental (`game === "standard"`) passe par `detectTechnique(r.text)`, calculé à l'affichage : pas de colonne en base, marche aussi pour les anciens rapports, et rien ne fuit en ligne puisque le rapport ne s'affiche qu'en fin de partie. Pas de conseil au nombre manquant (le calcul complet ne dit pas comment trouver le trou), au bon compte ni à la bombe. Sous la manche, un `<details className="rv-tip">` replié (« 💡 nom : morceau », mis en avant si on a raté le calcul) ouvre `TechniqueSteps` et les liens « Voir la technique » (`/learn?level=n#id`) et « S’entraîner » (`/learn/id`). En tête de revue : résumé `report.tipsSummary` et filtre « Avec une technique ».
- **Jeux à l'écran** : l'accueil et `/games` listent `GAME_IDS` (nom, règles, modes jouables) ; `/games` détaille aussi les modes et les niveaux. Chaque jeu de `/games` a un bouton « Jouer solo » vers `/solo?game=<id>` (la bombe : « Jouer en ligne »). `solo/page.tsx` valide `game` (jeu `solo` seulement) et le passe en `preset` à `SoloGame`, qui applique les derniers réglages de ce jeu (`local` `solo.<id>`, écrit à chaque changement), sinon `GAMES[g].defaults` au dernier niveau, remet l'adresse à `/solo` puis amène « Lancer la partie » à l'écran avec le focus.
- **Calcul du jour** : `/daily` (bouton de l'en-tête, `DailyCard` en tête de l'accueil tant qu'il n'est pas fini, résultat sur une ligne ensuite ; un invité est reconnu par le `local` `daily` de `@/lib/daily`). `DailyClient` suit les étapes du solo, mais chaque calcul vient de `POST /api/daily` : jamais de `GameEngine` ni de graine dans le navigateur, sinon les réponses fuiraient et le temps viendrait du client. Un seul essai ; une page rechargée reprend où elle en était, un calcul resté ouvert comptant comme temps écoulé. Jour à Paris, 5 calculs (Facile à Légende), temps de chaque niveau. Les corrections ne comptent pas dans le temps total, et une erreur ajoute son vrai temps. Invité : `/signup?next=/daily` ou `/login?next=/daily` (seule valeur de `next` suivie par `AuthForms`) ramènent à `/daily`, où `state` rattache l'essai au compte par son jeton. Classement sous le jeu, `?date=` pour un jour passé (`DailyBoardView`). Succès : `Achievements` sur le tableau de bord (les autres succès en cadenas) et le profil public.
- **Accueil** : titre, puis le calcul du jour, puis l'échauffement (`HeroCalc`, section `.warmup` titrée « Échauffement »), puis les deux grands choix. Sous 640 px, les choix passent avant l'échauffement, et sur écran tactile celui-ci reste replié (le calcul dans un bouton, sans pavé) jusqu'au premier toucher : en plein écran, le pavé passait pour le jeu. Styles dans `[locale]/home.css`, importé par la page seule.
- **Réglages** : `SettingsForm` propose d'abord le jeu (en solo, seulement les jeux `solo`) avec ses règles (`games.<id>.long`), puis les modes de ce jeu (explication du mode masquée pour un jeu à un seul mode, comme la bombe). `SoloGame` remplace un jeu réservé au en-ligne enregistré dans `localStorage` ; le lobby grise « Lancer » sous `minPlayers`. Dans la salle d'attente, les actions (« Lancer », « Je suis prêt », compte à rebours public, « Quitter ») et leur indication sont dans `.lobby-dock`, ancrée en bas de l'écran (`position: sticky`) : on règle la partie sans remonter pour la lancer.
- **Saisie** : `CalcLine` reçoit `puzzle` ; pour un nombre manquant, la case réponse prend la place du « ? » (l'énoncé complet reste dans `data-calc` de `calc-text`), et un opérateur se tape au clavier (`+ - * x / ÷`) ou sur `OperatorPad` en tactile. `answerFromInput` / `answerKindOfPuzzle` (`lib/answer.ts`) construisent la réponse envoyée. Au bon compte, `ExpressionBuilder` remplace `CalcLine` : cible, calculs intermédiaires posés (« = » ou Entrée : la ligne devient une étape et son résultat une nouvelle plaque, en pointillés), plaques à toucher, opérateurs permis, parenthèses, total partiel en direct ; ⌫ sur une ligne vide rouvre la dernière étape. `value` est la saisie en étapes (`readSteps`), `onSubmit(expr)` reçoit l'expression complète. OK dès qu'il y a un calcul (la ligne, ou la dernière étape si elle est vide ; toutes les plaques ne servent pas forcément) ; Entrée valide un total pile, sinon pose l'étape ; avec `allowClosest` (en ligne, simultané, à plusieurs), une Entrée sur ligne vide propose un total approché (deux Entrées : poser, puis proposer) (les symboles tapés au clavier sont réécrits : `*` → `×`). `TileExpression` reste la saisie d'une bombe. En fin de manche et dans le rapport, on affiche `solution` après `revealSeparator(game)` : `=` (calcul standard), `→` (nombre manquant), `:` (bon compte). Le rapport cache les statistiques par opération des jeux sans `operationStats`.
- **La bombe** (`BombStage.tsx`, en ligne seulement) : `BombBuild` (tirage, règles, `TileExpression` avec la valeur de la bombe en direct et la raison d'un refus, puis « Ta bombe » et « n / m bombes prêtes »), `BombAssign` (qui désamorce quoi), `BombPairList` (spectateurs), `BombResults` (fin de manche). Le désamorçage utilise `CalcLine`. `LobbyState.bombAck` garde la réponse du serveur à l'envoi. Réglage « Temps pour construire sa bombe » ; le choix simultané / chacun son tour est masqué pour un jeu sans `turns`.
- **Réglages par jeu** : choisir un jeu applique ses réglages par défaut du niveau (`GAMES[g].defaults`) ; le curseur de temps suit `GAMES[game].timeRange` ; le bouton parenthèses est masqué au bon compte.
- **Tactile** : `useTouch` décide entre saisie clavier et `Keypad` à l'écran. Toute touche de pavé (`Keypad`, `OperatorPad`, opérateurs et plaques de `ExpressionBuilder` / `TileExpression`) est un `PadButton` : l'action part au `pointerdown` (un `onClick` se perdait quand le doigt glissait ou se relevait à côté de la touche), le clic qui suit est ignoré, le clic clavier (`detail` 0) passe toujours ; CSS `touch-action: none` et pas de sélection. En partie, `PadDock` ancre le pavé en bas de l'écran (portail dans `body`, cale de même hauteur dans la page) : ses touches ne bougent pas, quel que soit le contenu au-dessus. Au bon compte et à la bombe, la saisie, l'indication et les plaques (deux rangées réservées) montent dans le pavé ; `OperatorPad` a la hauteur du pavé numérique, ⌫ et OK aux mêmes places. Le calcul de l'accueil (`HeroCalc`) garde son pavé dans la page (`CalcLine docked={false}`). `useGameOnScreen` (solo et lobby) ramène la page tout en haut pendant une partie et pose `data-playing` sur `<html>` : sur téléphone, `globals.css` retire alors l'en-tête et le pied de page, pour que le calcul tienne au-dessus du pavé, et remplace la cale par une marge en bas de `main` (`--pad-dock-height`, posée par `PadDock`), pour que le résultat et « Quitter » restent sous le calcul.
- **Profil** : `profile/layout.tsx` (en-tête photo, pseudo, date d'inscription, puis `ProfileTabs` en `.board-tabs`, badge du nombre de demandes d'ami) et quatre onglets, chacun revérifiant la session : `/profile/achievements` (voir Succès), `/profile` (photo, pseudo, e-mail en lecture seule, changement de mot de passe avec `revokeOtherSessions`, déconnexion, suppression), `/profile/friends`, `/profile/preferences` (langue, saisie, divisions). La langue n'est pas un champ du compte : comme le bouton de `HeaderTools`, elle change l'adresse (`router.replace(pathname, { locale })`). Le bouton de langue de l'en-tête n'est montré qu'aux visiteurs (`HeaderTools showLanguage`) : connecté, on passe par cet onglet.
- **Photo de profil** : recadrée en carré 256 px et encodée en WebP (JPEG sous Safari) par `squareAvatar` (`lib/avatar.ts`) ; `POST /api/avatar` vérifie la taille (`AVATAR_MAX_BYTES`) et la signature (`sniffImage`, le type annoncé ne compte pas), range les octets dans la table `avatar` puis pose `user.image = /api/avatar/<id>?v=<version>` via `auth.api.updateUser` (rafraîchit le cookie de session). `databaseHooks` refuse toute autre valeur de `image` (`INVALID_IMAGE`) et la vide à l'inscription. Jamais d'image en base64 dans `user.image` : elle finirait dans le cookie de session. `Avatar` (`PlayerChips`) affiche la photo si `image` est fourni, sinon l'initiale ; `getFriends` renvoie `image` pour les listes d'amis.
- **Amis** : onglet `/profile/friends` (`/friends` y redirige). « Inviter à une partie » crée un lobby avec les réglages en ligne habituels puis envoie l'invitation ; dans la salle d'attente, `InviteFriends` invite d'autres amis. `InviteNotice` (sous l'en-tête, connecté uniquement) interroge `/api/invites` toutes les 15 s et propose « Rejoindre » : les 3 invitations les plus récentes, puis le nombre des autres, qui remontent quand on en ignore une.
- **Guildes** : page `/guild` (lien « Guilde » de l'en-tête, pastille du nombre d'invitations reçues). Sans guilde : invitations reçues (rejoindre / refuser) et fondation. Dans une guilde : blason, nom et nombre de membres (le chef renomme, change ou retire le blason, recadré par `squareAvatar` comme une photo de profil), « Créer un lobby de guilde » (`createInviteLobby` de `@/lib/friends` puis `POST /api/guild/lobby` : une `GameInvite` avec `guildId` pour chaque autre membre, que `InviteNotice` annonce avec le nom de la guilde), membres en ligne puis hors ligne (le chef nomme un autre chef ou exclut), invitations par pseudo / e-mail ou parmi ses amis sans guilde (tout membre), invitations en attente (annulables par tout membre), quitter. La page se relit toutes les 30 s. **Présence** : `GET /api/invites`, appelé toutes les 15 s par `InviteNotice` (60 s en arrière-plan), met à jour `GuildMember.lastSeenAt` ; en ligne = moins de `GUILD_ONLINE_MS` (90 s). Constantes et `cleanGuildName` partagées avec le client dans `@calculus/db/guild`.
- **Lobbys publics** : `PublicLobbies` (colonne de droite de l'accueil, sous les deux grands choix en dessous de 1040 px) interroge `GET /lobbies` du serveur de jeu toutes les 3 s (`fetchPublicLobbies` de `@/lib/colyseus`) et lie chaque carte à `/lobby/<code>`. Dans `LobbyClient`, `snap.isPublic` remplace « Lancer » / « Je suis prêt » par le compte à rebours (`autoStartAt`), et en fin de partie propose « Trouver un autre lobby » (retour à l'accueil) au lieu de rejouer.
- **Bandeau du lobby** : la connexion à un lobby n'est pas coupée en quittant sa page (`current` dans `@/lib/colyseus`, suivi par `subscribeCurrentLobby` / `readCurrentLobby` ; rejoindre ou créer un autre lobby quitte l'ancien). `LobbyBanner` (sous l'en-tête, sur toutes les pages sauf celle du lobby) montre le code, le jeu, le mode, le niveau, les joueurs et quand la partie partira (compte à rebours public, attente de l'hôte, ou « Lancer » pour l'hôte), avec « Revenir au lobby » et « Quitter ». Dès que la partie démarre, il ramène au lobby pendant le compte à rebours de 3 s ; un lobby public dont on quitte le rapport est quitté. Un rechargement de page hors du lobby perd la connexion.
- **Joueurs connectés** : `OnlineCount` (dans le layout, en bas de la marge, collé pendant le défilement) lit `subscribeOnline` / `readOnline` de `@/lib/colyseus`, qui rejoint la salle de présence tant qu'un composant écoute et retente toutes les 15 s si le serveur de jeu est injoignable (rien n'est affiché alors). Le compte est par onglet, pas par personne. Les notes de page (`Margin`) vont dans `#margin-notes`, au-dessus.
- **Elo** : `GameReportView` reçoit `ratings` (snapshot du lobby ou `loadGameReport`) et affiche « Elo : avant → après » sous le verdict et dans le classement (`EloDelta`, vert / rouge), « placement n/5 » pendant le placement, puis l'Elo dévoilé à la 5e partie. Le tableau de bord montre la grille (jeu · mode) × difficulté et la variation de chaque partie récente.
- **Classement** : `/leaderboard` redirige vers `/leaderboard/<premier jeu>/<son premier mode>` ; `/leaderboard/<jeu>` ouvre son premier mode et l'ancienne adresse `/leaderboard/<mode>` mène au jeu `standard` (difficulté conservée). Onglets par jeu puis par mode (`.board-tabs`), difficulté et recherche dans l'URL (`?difficulty=1..5&q=pseudo`, validés par Zod, valeur invalide → défaut). Colonnes : place, joueur, Elo, parties, % de victoires. Page publique ; connecté, un bloc « Ta place » montre toujours sa ligne (place sur le nombre de classés, lien vers sa ligne `#board-me` s'il est dans le top), ou l'avancée de son placement.
- **Succès** : onglet `/profile/achievements` (`getAchievements`, filtres par catégorie, secrets affichés « ??? », progression des cumulatifs). L'ouverture appelle `POST /api/achievements/seen` puis rafraîchit : la pastille de l'onglet part, la mention « nouveau » reste sur la page. `GameReportView` reçoit `unlocks` (`snap.unlocks` ou réponse de `/api/solo-results`, jamais sur `/report/[id]`) : bloc de ses déblocages et son `sfx.unlock`, ligne « X a débloqué … » pour les autres. Le titre offert est mentionné. Paliers : jetons `--bronze`, `--silver`, `--gold`, `--platinum`.
- **Titres** : `PlayerTitle` affiche un id de titre (couleur selon la rareté, rien pour un id inconnu) sous le pseudo : en-tête du profil, `/player/[id]`, classement, lobby (`LobbyPlayer.title`) ; pas sur les pastilles en partie, pour garder l'écran de jeu compact. Tout compte a `newcomer` (`DEFAULT_TITLE_ID`) tant qu'il n'en a pas choisi d'autre ; « Aucun » n'affiche rien (`NO_TITLE`) ; un invité n'a pas de titre. `TitlePicker` (sous le pseudo, dans l'en-tête du profil, donc sur tous ses onglets) déroule les titres possédés, appelle `PATCH /api/profile/title` puis rafraîchit. Un titre changé pendant un lobby apparaît à la prochaine entrée : il voyage dans le jeton de `/api/game-token`.
- **Profil public** : `/player/[id]`, ouvert en cliquant un pseudo du classement. Montre ce que le classement rend déjà public (pseudo, et pour chaque jeu × mode × difficulté classé : place, Elo, parties, % de victoires) et les succès (nombre, six des paliers les plus hauts), via `getPlayerProfile`. Bouton d'ami selon le lien (`FriendshipState`) : ajouter (`POST { userId }`), annuler, accepter / refuser, ou « vous êtes amis » ; visiteur → lien de connexion.
- **Textes légaux** : `/legal` (mentions légales), `/privacy` (confidentialité), `/terms` (CGU), rendus par `LegalPage` depuis `legal.<doc>.sections` des messages (`t.raw` : paragraphes, ou tableaux = listes ; marqueurs `{publisher}` / `{contact}` remplis depuis `@/lib/legal`). Liens dans `Footer` et case obligatoire à l'inscription. Changer `LEGAL_UPDATED` à chaque modification de fond, et mettre la politique de confidentialité à jour à chaque nouvelle donnée collectée ou nouveau prestataire.
- **Suppression de compte** : `user.deleteUser` de Better Auth (mot de passe demandé dans le profil). `beforeDelete` appelle `eraseUserGames` (db) : parties solo supprimées, pseudo vidé dans les parties en ligne (`GameReportView` affiche alors `report.deletedPlayer`) ; le reste part en cascade.
- **Versions et nouveautés** : `RELEASES` (`@/lib/releases`) est la seule source du numéro de version (`APP_VERSION`, la première entrée) ; les notes de chaque version sont dans `changelog.notes.<releaseKey(version)>` (`v1_1_0` : pas de point dans une clé next-intl), lues par `t.raw` sur `/changelog`. Lien « Nouveautés · vX.Y.Z » dans `Footer`. `ReleaseNotice` (sous l'en-tête, comptes et invités) s'affiche moins de 48 h après la mise en production (`NEXT_PUBLIC_RELEASED_AT`, heure du build posée par `next.config.ts`) tant que `local` `release.seen` n'est pas la version en ligne ; ouvrir `/changelog`, fermer le bandeau ou une première visite (sans bandeau : il décalerait la page) l'y écrit. **À chaque mise en production avec des nouveautés** : ajouter la version en tête de `RELEASES` et ses notes dans les deux langues.
- **Retours** : `/feedback` (lien dans `Footer`, `?from=<chemin>&kind=bug|idea` facultatifs), ouvert aux invités. `POST /api/feedback` : Zod, champ piège `website` (doit rester vide), chemin interne seulement, limite horaire en base (`createFeedback` : 10 par compte, 60 pour l'ensemble des invités, aucune IP enregistrée). Les constantes partagées avec le formulaire client sont dans `@calculus/db/feedback` (sans Prisma).
- **Panel administrateur** : `/admin`, réservé aux comptes dont l'id figure dans `ADMIN_USER_IDS` (`isAdminUser` / `getAdminSession` / `requireAdmin` de `@/lib/admin`). Pour les autres, les pages répondent 404 et les routes `api/admin/*` 403. **Chaque page appelle `requireAdmin()`** (le layout ne suffit pas : il n'est pas rejoué à chaque navigation). Lien « Admin » dans `Header` pour les administrateurs. Onglets : vue d'ensemble (inscrits, parties jouées par jour ou par semaine, solo et en ligne, sur 30 jours, 90 jours ou 12 mois via `?range=`, inscriptions par jour sur 30 jours, parties, retours à traiter), parties en ligne (`LiveGames`, rafraîchi toutes les 5 s, puis `GamesHistory` : parties enregistrées paginées via `?page=`, lues dans `Game` / `GamePlayer`, sans table dédiée : une partie interrompue avant `finish()` n'y figure pas), parties solo (`SoloPlays`, rafraîchi toutes les 10 s : en cours, dernières parties, compteurs 24 h ; alimenté par `SoloActivity` de `lib/soloActivity.ts` dans `SoloGame`), retours (filtre à traiter / traités / tous, traiter, supprimer), comptes (recherche pseudo ou e-mail, fiche avec le `DashboardView` du joueur). Jamais d'e-mail pour désigner un administrateur : ils ne sont pas vérifiés à l'inscription, n'importe qui pourrait prendre une adresse restée sans compte. Pour en ajouter un : créer son compte, lire son id (`pnpm db:studio` ou SQL), l'ajouter à `ADMIN_USER_IDS`.
- **Parties en cours** : `fetchLiveRooms` signe un JWT d'une minute (`GAME_TOKEN_SECRET`, audience `calculus-admin`) et appelle `GET /admin/rooms` du serveur de jeu, à l'adresse HTTP déduite de `NEXT_PUBLIC_GAME_SERVER_URL` (`ws` → `http`, `wss` → `https`).
- **Dictée** : réglage de compte `User.voiceInput` (champ additionnel Better Auth, modifiable depuis le profil). `CalcLine` lance `useVoiceInput` (Web Speech API, pas de Firefox) qui remplit la case via `parseSpokenNumber` ; la validation reste à la touche Entrée (ou OK sur le pavé).
- **Affichage des divisions** : réglage de compte `User.divisionDisplay` (`"standard"` ou `"fraction"`, liste dans `@/lib/division`, valeur refusée par `databaseHooks` sinon, code `INVALID_DIVISION_DISPLAY`), modifiable depuis le profil. En fraction, `MathText` / `FractionExpr` (`components/MathText.tsx`) écrivent chaque « a ÷ b » avec une barre (parenthèses de l'énoncé retirées dans le dividende et le diviseur) : énoncé de `CalcLine` (la case d'un nombre manquant se place dans la fraction ; un opérateur manquant reste en ligne) et lignes du rapport. `data-calc` garde toujours le texte d'origine.
- **Conseils de fin de partie** : réglage de compte `User.showTips` (vrai par défaut), « Conseils en fin de partie » dans `/profile/preferences` (Afficher / Désactiver l’aide). `useShowTips` (`@/lib/tips`) le lit dans la session ; pour un invité, `local` `calculus:tips`. Le rapport n'affiche rien tant que la session n'est pas connue ; « Ne plus afficher les conseils » dans le résumé de la revue coupe le réglage (compte ou navigateur) ; un invité les réaffiche au même endroit, un compte depuis ses préférences.
